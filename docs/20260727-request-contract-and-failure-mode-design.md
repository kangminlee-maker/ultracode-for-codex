## Part 1. 진단 — 두 실패면이 서로 반대로 틀렸습니다

전역 규범은 이렇게 말합니다.

> 결정론적으로 판정 가능한 구조·보안 위반만 하드블록하고, 의미·품질·커버리지 문제는 사용자가 판단할 비차단 공지로 보낸다.

현재 구현은 이것이 **뒤집혀** 있습니다.

| 계층 | 오류의 성격 | 판정 시점 | 규범이 요구하는 동작 | 현재 동작 |
| --- | --- | --- | --- | --- |
| 요청 인자 (`--args`) | 결정론적으로 판정 가능 | 에이전트 스폰 **이전**, 비용 0 | **하드블록 (fail-loud)** | **조용히 강제 변환·무시** |
| 에이전트 출력 ref | 의미적, 사후에만 알 수 있음 | 지출 **이후** | **비차단 공지 (fail-safe)** | **런 전체 중단** |

### 1.1 요청 인자 계층 — 조용히 삼킵니다 (실측)

`code-review`의 인자 처리부는 3줄입니다(`workflow-runtime.ts:765-769`). 검증은 없고 폴백만 있습니다. 실제로 돌린 결과:

| `--args` | 관측된 결과 | 문제 |
| --- | --- | --- |
| `{}` | scope effort `xhigh` | 기본값 (정상) |
| `{"level":"high"}` | `medium` | 문서화된 값 (정상) |
| `{"level":"medium"}` | **`xhigh`** | 더 싸게 요청했는데 **가장 비싼 프로파일** |
| `{"level":"HIGH"}` | **`xhigh`** | 대소문자 하나로 조용히 최고가 |
| `{"promt":"인증 경로 리뷰"}` | 기본 프롬프트로 실행 | **의도가 완전히 소실된 채 성공** |
| `{"diffBase":"HEAD~1"}` | 조용히 무시 | 키 이름 오타를 알려주지 않음 |
| `{"diffBaseRef":"nope"}` | 조용히 무시 + 프롬프트에 `unavailable:diff-base` 토큰만 | 커밋 증거 없이 리뷰가 진행됨 |
| `{"reviewDepth":"max"}` | 조용히 무시 | 미지의 키를 거부하지 않음 |

가장 나쁜 것은 `{"promt":...}`입니다. **실패하지 않고, 사용자가 요청하지 않은 리뷰를 수행하고, 성공으로 보고합니다.** fail-loud도 fail-safe도 아니고 fail-silent-and-wrong입니다.

`level` 오타 한 번의 대가는 실측 기준 scope `medium`→`xhigh`, 렌즈 8→10, sweep 단계 추가, 보고 상한 10→15입니다.

### 1.2 에이전트 출력 계층 — 문자열 하나로 런 전체를 버립니다

`failUnsupportedRef`(`:940-941`)는 `fail()`을 호출하고, 이는 워크플로 전체를 종료시킵니다. 호출 지점은 Scope(`:969`), 후보마다(`:998`), 그리고 증거·결정 ref 검증입니다 — 즉 **합성 단계에서 걸리면 그때까지의 모든 에이전트 결과가 버려집니다.**

그런데 이 머신에 남은 실제 거부 2종은 **범위 위반이 아니라 문법 오류**였습니다(독립 검증 문서 Part 3, 재확인 완료):

- `file:…design.md:74` — 허용목록에 `file:…design.md`가 이미 있었고, 모델이 `파일:줄` 관습대로 `:74`를 붙였을 뿐
- `diff:unstaged:…service.ts` — 같은 파일이 `file:`로는 허용목록에 있었고, `diff:unstaged:` 종류로는 생성되지 않았을 뿐

두 경우 모두 **인용된 경로 자체는 허용 집합 안에 있었습니다.** 페일클로즈가 막으려는 것(존재하지 않는 파일을 인용하는 환각)은 발생하지 않았습니다. 막힌 것은 문자열 형식입니다.

게다가 어떤 종류(`file:` / `diff:<kind>:` / `hunk:<kind>:<n>`)가 존재하는지는 그 파일이 미추적인지 unstaged인지 staged인지에 달려 있고, **모델은 그 정보를 받지 못합니다.** 알 수 없는 것을 맞히도록 요구하고, 틀리면 런을 죽입니다.

### 1.3 원인 진단이 불가능합니다

게이트 실패 메시지는 `no reviewable change evidence in the working tree`까지만 말합니다. 확장자 필터에 걸렸는지, 제외 디렉터리에 걸렸는지, 정말 변경이 없는지 구분되지 않습니다. `.java`만 수정한 사용자는 원인을 찾을 수 없습니다.

### 1.4 사전 확인 수단이 없습니다

`--validate`는 `validateWorkflowInput`을 호출하는 **정적** 검사입니다(에이전트 호출부 수, 스키마 수, 경고). 스크립트를 실행하지 않으므로 **"이 요청이 실행될 것인가"를 미리 물어볼 방법이 없습니다.** LLM 호출자는 지출해 봐야 압니다. (`PREFLIGHT_BACKEND`는 이미 존재하므로 재료는 있습니다.)

## Part 2. 설계 원칙

1. **판정 시점으로 실패 방식을 정한다.** 지출 전에 결정론적으로 판정 가능하면 하드블록. 지출 후에만 알 수 있는 의미 문제면 강등 + 공지.
2. **보존해야 하는 성질만 보존한다.** ref 검증의 목적은 "허용되지 않은 **경로**를 인용하는 환각 차단"이다. 종류·접미사 엄격성은 그 성질을 지키는 데 필요하지 않다.
3. **알 수 없는 것을 요구하지 않는다.** 모델이 볼 수 없는 정보로 문자열을 맞히게 하는 대신, 런타임이 문법을 알려주거나 관용적으로 대조한다.
4. **거부는 원인과 처방을 말한다.** 이미 `failUnsupportedRef`가 그 형식을 갖췄으므로(값·집합·출처·무엇이 채우는가) 게이트 실패도 같은 형식을 따른다.
5. **동작을 바꾸는 변경은 기본 off 뒤에 둔다.** off일 때 현재 동작과 diff로 동일함이 증명되어야 한다.

## Part 3. 설계 — 9개 변경, 4개 그룹

### Group 1 — 요청 계약을 시끄럽게 (지출 전, 토큰 0)

**R1. 빌트인별 인자 계약 선언 + 런치 시점 검증**

각 빌트인이 받는 키를 런타임이 알고 있게 하고, 런치에서 검증합니다.

| 검사 | 동작 |
| --- | --- |
| 미지의 키 | 거부. 메시지에 **허용 키 목록**을 나열 |
| 오타 키 | 거부 + 편집거리 1 이내 후보 제시 (`promt` → `prompt` 아닙니까?) |
| `level` 값 | 런타임 enum. `high` / `xhigh` 만 유효(둘 다 명시 가능), 대소문자 무관 수용, 그 밖은 거부하며 **두 유효값을 명시** |
| `prompt` 타입 | 문자열 아니면 거부 (현재는 조용히 기본값) |

`level`에 `xhigh`를 명시적 값으로 추가하는 것은 개념 추가가 아니라 **기존 기본값에 이름을 주는 것**입니다. 지금은 "생략"만이 깊은 프로파일을 뜻해서 호출자가 의도를 표현할 수 없습니다.

**R2. `diffBaseRef`를 런치에서 해석**

`git rev-parse --verify <ref>^{commit}`은 결정론적이고 지출 전에 가능합니다. 실패하면 거부하고 거부된 값을 그대로 보여줍니다. 현재처럼 조용히 커밋 증거 없이 진행하지 않습니다.

**R3. `--validate`에 증거 전제조건 리포트 추가 (핵심 레버)**

`PREFLIGHT_BACKEND`로 증거 수집까지만 실행하고 결과를 구조화해 출력합니다. 에이전트 0개, 토큰 0.

```json
{ "kind": "ultracode.workflow.validate", "status": "valid",
  "evidence": {
    "gated": true,
    "reason": "no reviewable change evidence in the working tree",
    "changedPaths": 3,
    "allowedFileRefs": 0,
    "dropped": [
      { "path": "src/App.java",     "rule": "extension-not-allowed" },
      { "path": "Dockerfile",       "rule": "extension-not-allowed" },
      { "path": "dist/bundle.js",   "rule": "excluded-dir" } ],
    "allowedEvidenceRefs": [] } }
```

LLM 호출자에게 이것이 가장 큰 변화입니다 — **지출 전에 "실행되는가, 무엇을 보게 되는가"를 물어볼 수 있습니다.**

### Group 2 — 게이트 실패가 원인을 말하게

**R4. 드롭 사유별 집계를 실패 메시지에 포함**

```
code-review invalid: no reviewable change evidence in the working tree:
allowed file refs is empty (0 entries); git status reported 3 changed paths,
all dropped — 2 by the evidence extension allowlist (src/App.java, Dockerfile),
1 by the excluded-directory rule (dist/bundle.js).
Remediation: change a file whose extension is in the allowlist, or run with
--evidence-scope all.
```

게이트를 통과했지만 일부가 드롭된 경우는 실패가 아니므로, 증거 컨텍스트에 `### Dropped From Evidence` 절로 비차단 공지합니다. 리뷰 에이전트가 "이 파일은 인용할 수 없다"를 알게 되어 헛짚지 않습니다.

### Group 3 — 출력 측 거부를 회복 가능하게

**R5. 거부 전에 정규화 + 경로 단위 대조**

순서: ① 완전 일치 → ② `file:<path>:<n>`의 후행 `:<n>` 제거 후 재대조 → ③ 종류를 무시하고 **경로**가 허용 경로 집합에 있으면 통과(정규화된 ref로 치환) → ④ 그래도 없으면 거부.

관측된 실제 거부 2종이 모두 ②·③에서 살아납니다. 그리고 ④는 그대로 남으므로 **환각 차단 성질은 손실 없이 보존됩니다** — 경로가 증거에 없으면 여전히 거부입니다.

**R6. 잔여 무효 ref는 런을 죽이지 않고 강등**

해당 후보/발견만 드롭하고 `stats.droppedRefs[]`에 거부값·사유를 기록하며 런 결과에 공지합니다. 단, **워크스페이스 이탈 경로(`../`, 절대경로) 등 구조·보안 위반은 계속 하드블록**합니다 — 이쪽은 결정론적으로 판정 가능한 위반이므로 규범상 하드블록 대상입니다.

**R7. 프롬프트가 ref 문법을 명시**

런타임이 소유하는 한 줄을 증거 컨텍스트에 추가합니다: 허용목록의 문자열을 **그대로** 쓸 것, 줄번호를 덧붙이지 말 것, 목록에 없는 종류는 존재하지 않음. 지금은 목록만 주고 문법은 추측하게 합니다.

### Group 4 — 범위: 유연성의 실제 병목

**R8. 술어 분리 — 증거용과 프롬프트 예산용**

`shouldIncludeWorkspaceContextPath`는 원래 "프롬프트에 인라인할 텍스트 파일 고르기"용이었고(루트 커밋 `56d3c73`, 호출부 1곳), `76e54e6`에서 런타임 상태 배제를 구현하며 증거 경로에 재사용되면서 확장자 허용목록이 **리뷰 범위 정책으로 승격**됐습니다.

분리합니다:

| 술어 | 결정 대상 | 디렉터리 제외 | 확장자 필터 |
| --- | --- | --- | --- |
| `shouldIncludeWorkspaceContextPath` (유지) | `### Included Files` 예산 | 함 | **함** |
| `evidencePathAllowed` (신규) | `allowedEvidenceRefs`, 게이트 | 함 | **안 함** |

효과: `.java`·`.kt`·`.rb`·`.php`·`.sql`·`.vue`·`.tf` 프로젝트가 리뷰 가능해집니다. Part 1의 status/증거 비대칭이 근본에서 사라집니다.

비용 통제는 그대로입니다 — 프롬프트 바이트를 지배하는 것은 `### Included Files`(500개 walk 절단 + `maxBytes`)와 diff 바이트 상한이고, 둘 다 이 변경이 건드리지 않습니다. 확장자 목록은 애초에 diff 크기를 제한한 적이 없습니다.

**R9. `diffBaseRef`가 해석되면 커밋 ref를 게이트에 포함**

게이트가 `file:` ref만 세기 때문에 워킹트리가 깨끗하면 커밋된 변경만 리뷰하는 것이 불가능합니다. `diffBaseRef`가 유효할 때 `diff:committed:*`를 게이트 계산에 포함시켜, PR 브랜치·직전 커밋 리뷰를 가능하게 합니다. `diffBaseRef` 없는 경우의 동작은 바뀌지 않습니다.

## Part 4. 결정이 필요한 항목 2개

| | 선택지 | 권고 |
| --- | --- | --- |
| **D1. R8 기본값** | (a) 기본 확대 (b) `--evidence-scope all` 옵트인, 기본은 현재 동작 | **(b) 먼저, 다음 릴리스에서 (a)** — 동작 변경을 기본 off 뒤에 두는 규범을 지키고, 도그푸드 후 뒤집기 |
| **D2. R6 기본값** | (a) 기본 강등 (b) `--ref-policy lenient` 옵트인 | **(b)** — R5가 관측된 실패 2종을 이미 살리므로 R6의 즉시 이득은 작고, 페일클로즈 완화는 되돌릴 수 있게 두는 편이 낫다 |

R1–R5, R7, R9는 옵션이 필요하지 않습니다. 조용했던 것을 시끄럽게 만들거나(R1·R2·R4), 없던 확인 수단을 추가하거나(R3), 보존해야 하는 성질을 유지한 채 문법 엄격성만 낮추거나(R5·R7), 불가능했던 요청을 가능하게 하는 것(R9)이므로 기존 성공 경로를 깨지 않습니다.

단 R1은 **의도적 파괴 변경**입니다. 지금 `{"promt":...}`로 호출하던 코드는 실패하게 됩니다 — 그것이 이 변경의 목적입니다.

## Part 5. 구현 순서와 검증 게이트

| 단계 | 내용 | 의존 | 검증 |
| --- | --- | --- | --- |
| S1 | R1 + R2 인자 계약 | — | 거부 케이스별 메시지 단위 테스트 + **음성 대조**: `{"level":"high"}`가 여전히 scope `medium`을 내는지 |
| S2 | R4 드롭 사유 집계 → R3 preflight 리포트 | S1 | preflight가 `gated=true` + 드롭 사유를 내고 **백엔드 호출 0**임을 단정 |
| S3 | R5 + R7 ref 정규화·문법 | — | 디스크의 실제 거부 2종을 픽스처로 재생 → 통과. **음성 대조**: `file:not-in-tree.md`는 여전히 거부 |
| S4 | R9 커밋 ref 게이트 포함 | S1(R2) | 깨끗한 트리 + 유효 `diffBaseRef` → 통과. `diffBaseRef` 없으면 여전히 차단 |
| S5 | R8·R6 플래그 (D1·D2 결정 후) | S2, S3 | 플래그 on/off로 `file:src/App.java` 존재/부재 대조 — **플래그가 실제로 배선됐음을 증명** |
| S6 | 스킬·LLM 가이드 문서 갱신 | S1–S5 | `skills/*/SKILL.md`의 클린 트리 문구 + 새 계약 반영 |

각 단계마다 `npm test`(lint+build+unit 143건 기준선), CLI 출력을 건드리는 단계는 `test:all`(e2e). 머지 전 교차 계열 리뷰(Codex)와 PR 봇 리뷰를 게이트로 둡니다.

### 검증 원칙

- 모든 "거부한다" 주장은 **거부되지 않아야 하는 입력**의 대조군과 짝지어야 합니다. 대조군 없는 거부 테스트는 전량 거부하는 구현으로도 통과합니다.
- S5의 플래그 테스트는 on/off 양방향을 단정해야 합니다. 한쪽만 보면 플래그가 무시되는 구현도 통과합니다.
- S3의 픽스처는 추상 예시가 아니라 **디스크에 실제로 남은 거부값**을 씁니다.

## Part 6. 이 설계가 남기는 것

호출자(LLM) 입장에서의 변화:

| 지금 | 이후 |
| --- | --- |
| 오타가 조용히 무시되고 엉뚱한 리뷰가 성공한다 | 런치에서 거부되고 올바른 키를 알려준다 |
| 실행될지 알려면 지출해야 한다 | `--validate`로 무료로 묻는다 |
| `.java` 프로젝트에서 왜 안 되는지 알 수 없다 | 실패 메시지가 어떤 규칙이 무엇을 드롭했는지 말한다 |
| `.java` 프로젝트를 리뷰할 수 없다 | (D1 이후) 리뷰할 수 있다 |
| 마지막 단계의 문자열 하나로 런 전체를 버린다 | 정규화로 살리고, 못 살리면 그 발견만 드롭하고 공지한다 |
| 커밋된 변경을 리뷰할 수 없다 | `diffBaseRef`로 가능하다 |

다루지 않는 것: 리뷰 품질·재현율, 렌즈 선택 로직, 비용 튜닝. 이 설계는 **요청 계약과 실패 모드**만 다룹니다.
